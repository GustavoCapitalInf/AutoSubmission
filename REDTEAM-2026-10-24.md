# Red team assessment — bank-statement-tryout.fly.dev

Date: 2026-10-24. Scope: the deployed intern-testing webapp at
https://bank-statement-tryout.fly.dev (Fly machine `shared-cpu-1x`, 1 GB, no swap,
volume `webapp_data`), acting as an external bad actor with only public reachability
and the repository checkout. All uploaded test documents were fabricated
(CONTOSO); no customer statement data was used or exposed. Every finding below
was reproduced, not inferred, except where noted.

## Method

1. Read the deployed contracts (`docs/intern-testing.md`, `webapp/auth.py`,
   `webapp/app.py`, `webapp/intake.py`, `ocr/rasterize.py`, `fly.toml`) to map the
   attack surface.
2. Unauthenticated recon of the live host: probe, auth behavior, headers,
   TLS, rate limiting, user enumeration.
3. Credential attack: the checkout's local `.env` (untracked) holds
   `WEBAPP_AUTH_PASSWORD` marked "retired 2026-10-19 with the local tunnel
   host". Tried it against the Fly host.
4. Authenticated attacks on a local instance of the same code (same app
   version `?v=true-revenue-18`), then confirmed the worst finding on the live
   host.
5. Crafted-PDF attacks: giant CropBox pages (memory/CPU DoS), storage-fill
   arithmetic, filename injection (`--!>` HTML5 comment close), CSRF on
   `/upload` via foreign-`Origin` multipart POST.

## Findings

Severity is the risk to company/customers when this host (or this code) is
released for real use.

### RT-1 (CRITICAL) — Retired password still opens the public host

The shared HTTP Basic password recorded in the local `.env` as retired with the
old tunnel host authenticates on the Fly host today:

```
curl -u intern:<retired .env password> https://bank-statement-tryout.fly.dev/api/settings
→ 200 {"settings":{...}}
```

Any past holder of the tunnel password (including ex-interns) retains full
access to every uploaded statement on the public internet: view, download, re-
analyze, re-review. The gate the whole design rests on has silently lapsed.

Remediation: rotate `WEBAPP_AUTH_PASSWORD` on Fly now; never reuse a secret
across hosts; before release, replace the shared password with per-user
credentials (already planned as D-2b production auth).

### RT-2 (HIGH, reproduced live) — One crafted PDF can OOM-kill the machine, repeatedly

`/page/<job_id>/<n>` rasterizes a stored PDF at a fixed 100 dpi with no bound
on page size and no timeout (`ocr/rasterize.py::rasterize_page`). A PDF whose
CropBox is 100×100 inches (7200×7200 pt) rasterizes to 10,000×10,000 px —
~300 MB of pixel data per request on a 1 GB machine with no swap. A 200×200 in
page needs ~1.2 GB and PIL only rejects it *after* Poppler has already rendered
it (500 after the cost is paid).

Reproduced on the live host (job ids for cleanup below): a 506-byte PDF with a
7200×7200 CropBox. First `/page` request served the raster (HTTP 200, 5.0 s);
the next two requests each killed the machine (HTTP 502, Fly auto-restarted
it). Anyone with the password can sustain a kill loop with ~500-byte requests,
and the machine burn also costs money. Worse: the dashboard fetches `/page` for
every page of a statement it opens, so merely opening the crafted statement in
the UI triggers the kill — the attacker does not even need to keep sending
requests. The upload path is also affected: a scanned-looking giant page would
rasterize at 300 dpi into a multi-GB PPM on disk during analysis.

Remediation: bound the page at intake (reject CropBox/MediaBox beyond a sane
paper size, e.g. > 200 in or > 100 Mpx at 100 dpi), cap raster output (pass
`-scale-to`/pixel limits to `pdftoppm`), and pass a `timeout` to
`rasterize_page` so a hung page cannot pin a thread.

### RT-3 (HIGH) — CSRF on /upload: a drive-by can plant statements (and RT-2 PDFs)

Every state-changing browser route except `/upload` was hardened to JSON-only
(needs a preflight, so cross-site HTML forms cannot reach it). `/upload` still
accepts a plain multipart form, and the browser attaches cached Basic
credentials to form posts. No `Origin`/`Referer` validation, no token:

```
curl -u intern:<password> -H "Origin: https://evil.example" \
  -F "files=@junk.pdf" https://bank-statement-tryout.fly.dev/upload → 200
```

An attacker page can auto-submit such a form against every intern that visits it
while their browser holds the Basic credential cache. Chained with RT-2 this is
a drive-by machine-killer; chained with RT-4 it silently fills the volume.

Remediation: require JSON/fetch with preflight for `/upload` (same pattern as
the review routes), or validate `Origin`/`Referer` on the POST, or issue a
per-session CSRF token in the page.

### RT-4 (HIGH) — Storage exhaustion is permanent and requires no skill

Nothing ever deletes a job, document, PDF or artifact (by design; retention is
an owner decision). Intake allows 100 MB × 25 files per request, unlimited
requests, and the only guard is the 256 MB free-space floor (`MIN_FREE_MB`),
after which uploads are refused with 507 until an owner intervenes. Content
dedup does not help: appending one random byte defeats it. Verified locally:
each 20 MB fabricated upload added ~21 MB to the data dir, forever. An
intern — or a CSRF'd visitor (RT-3) — can take the host to the 507 state in a
lunch break, and a filled volume also degrades SQLite durability behavior.

Remediation: per-uploader quotas, a retention/expiry policy or an owner purge
path, volume-size monitoring and alerting, and a Fly volume sized with
headroom before release.

### RT-5 (MEDIUM) — No rate limit, no lockout: the shared password is brute-forceable

Sent 60 bad Basic attempts in 21 s against the live host: no 429, no lockout,
no delay; attempt 61 was answered normally. Username enumeration is not
possible (wrong user and wrong password answer identically, timing flat, thanks
to `compare_digest`). But with a single shared password and unlimited attempts,
offline-rate brute force is only a matter of time, and Fly auto-starts the
machine for the attacker so it costs nothing to grind.

Remediation: rate-limit auth failures at the app or Fly proxy; better, move to
per-user credentials (D-2b) so one leaked password is not the whole castle.

### RT-6 (MEDIUM) — The dashboard ships no security headers

`GET /` (authenticated) returns no `Content-Security-Policy`, no
`X-Frame-Options`/`frame-ancestors`, no `Strict-Transport-Security`, no
`X-Content-Type-Options`, no `Referrer-Policy`. Consequences: the review UI
("Confirm Revenue" decisions) can be framed and clickjacked on an attacker page
(Basic credentials ride along with iframe loads), and the first-visit HTTP→HTTPS
hop relies on Fly's redirect alone. The report routes are well hardened (CSP
`sandbox` + `nosniff`) — the dashboard is the gap.

Remediation: add a global CSP (no `unsafe-inline` script needed beyond the
existing bundle), `frame-ancestors 'self'`, HSTS, `nosniff` and
`Referrer-Policy` at the app or Fly proxy level.

### RT-7 (MEDIUM, documented residual — restated for release) — One password reads every statement

There are no per-user accounts and no tenant isolation: every uploaded
statement, its raw OCR text (account numbers included, `webapp/app.py` /
`markdown` residual Wave 0), its analyses and downloads are reachable by
anyone holding the one shared password, and review audit rows record only a
free-text actor (`local-analyst` default). Fine for intern QA; unacceptable
for customer use. Downloads are audit-logged (`record_export`), which helps.

Remediation: D-2b (per-user auth, attribution) is the release gate; until
then, treat every credential holder as having read access to all documents.

### RT-8 (LOW, defended — verified) — Filename and text-layer injection attempts

Tried: a filename using the HTML5 `--!>` comment close (intake bans only
`-->`) carrying `<b>`/`onerror` payloads, and reviewed the text-layer path.
Both are defended: the report title is `html.escape`d, the provenance comment
is escaped by `render_fragment` (`_neutralize_markup`), the dashboard escapes
every filename sink found (`escapeHtml` throughout `app.js`), and the report
CSP (`default-src 'none'`, `sandbox`) blocks script even if something slips.
No injection achieved. Noted only as a defense-in-depth check that passed.

### RT-9 (LOW) — Minor information exposure

`/healthz` and the unauthenticated `/api/v1/*` `api_disabled` response reveal
deployment state (API off) but no document data. Acceptable.

## What was checked and found solid

- Loopback/fail-closed bind rule, JSON-only settings/review/reanalyze routes
  (preflight blocks cross-site forms there), `compare_digest` on both Basic
  fields, bearer-API disabled on this host with a distinct-token rule,
  upload validation (size/pages/magic/encryption, nothing stored on refusal),
  filename header sanitization (`_safe_download_name`), escaped dashboard and
  report rendering, report CSP sandbox + inert HTML download, Werkzeug dev
  server never used, waitress only.

## Remediation status

Fixed in code (the hardening pull request that carries this report):

- **RT-2** — intake refuses a page wider or taller than 25 inches
  (`webapp/intake.py::MAX_PAGE_POINTS`, refusal code `page_too_large`, surfaced
  in the machine API contract); `/page` rasterization carries a 120 s
  timeout so a hung page cannot pin a thread.
- **RT-3** — a state-changing browser request that names another site
  (`Origin`/`Referer`) is refused with 403 (`webapp/auth.py::cross_site_refusal`);
  `Origin: null` is refused too; requests that name no site (curl, the
  machine API) are unchanged.
- **RT-6** — every response carries `nosniff`, `Referrer-Policy`,
  `X-Frame-Options: SAMEORIGIN` and HSTS; HTML pages without their own CSP
  get a dashboard CSP whose only inline-script allowance is the theme
  bootstrap's content hash (`webapp/app.py::DASHBOARD_CSP`); the report
  routes keep their stricter `sandbox` policy.

Operational, for the owner (not code):

- **RT-1** — rotate `WEBAPP_AUTH_PASSWORD` on Fly
  (`fly secrets set WEBAPP_AUTH_PASSWORD=<new> -a bank-statement-tryout`) and
  stop reusing secrets across hosts.
- **RT-4** — decide retention before release: quotas, expiry or an owner
  purge path, plus volume-size alerting. The fabricated test jobs listed
  above can go in that first purge.
- **RT-5** — rate-limit auth failures (Fly proxy or an app-level limiter)
  until per-user credentials (D-2b) land.
- **RT-7** — unchanged: D-2b per-user auth remains the release gate.
