# Lender matching API v1

Auto-Submission (`apps/auto_submission/`) sends a deal's application facts and its bank statement analysis package
id to this server and reads back, for every lender, whether the deal meets the lender's current criteria and why.
This document is the contract between them. The request and response types are the `lender_matching_wire` crate
(`wire/src/v1.rs`). `docs/api/v1.schema.json` and the reference at the end of this page are generated from that
crate by `cargo run -p lender_matching_wire --example write_contract`, and the `contract_files_are_current` test
fails when either is stale.

## Call it

The base URL is `https://<host>/api/v1`. Every request sends a named token as a bearer token.

```http
POST /api/v1/matches
Authorization: Bearer <token>
Content-Type: application/json

{
  "analysis_package_id": "0f8fad5b-d9cb-469f-a165-70867728950e",
  "product": "mca",
  "application": {
    "business_state": "TX",
    "business_start_month": "2021-04",
    "entity": "llc",
    "estimated_fico": {"min": 640, "max": 640},
    "requested_amount_cents": 7500000,
    "open_judgements": false,
    "bankruptcy": false,
    "tax_liens": false,
    "industry_suggestion": "construction-contractor"
  }
}
```

The answer is `201 Created` with `Location: /api/v1/matches/<match_id>` and the stored match. Read it again later
with `GET /api/v1/matches/<match_id>`.

```json
{

  "match_id": "5b0e3c1a-7d1f-4a43-9c55-3f1f0b7e2a90",

  "created_by": {"kind": "client", "name": "auto-submission"},
  "supersedes": null,
  "superseded_by": null,
  "as_of": "2026-10-23",
  "engine_version": 1,
  "product": "mca",
  "analysis": {"package_id": "0f8fad5b-d9cb-469f-a165-70867728950e", "revision": "9c1d…e4"},

```

A loop that waits for the analysis looks like this:

```rust
loop {
    let response = http.post(format!("{base}/matches")).bearer_auth(&token).json(&request).send().await?;
    match response.status().as_u16() {
        201 => break response.json::<lender_matching_wire::v1::MatchResponse>().await?,
        409 => tokio::time::sleep(retry_after(&response)).await,   // analysis_not_ready
        _ => return Err(response.json::<lender_matching_wire::v1::ErrorResponse>().await?.into()),
    }
}
```

## Set up a token

The operator creates one token per client on the server host and gives it to that client once:

```bash
lender-matching token create auto-submission --scope match --scope read   # prints the token once
lender-matching token revoke auto-submission                               # it answers 401 from then on
```

- `match` opens `POST /matches`. `read` opens `GET /industries` and `GET /matches/<id>`. A token without the scope a
  request needs answers 403 `scope_required`.
- The token is stored only as its SHA-256 digest. Each match records the client that made it.
- A request sends `Authorization: Bearer <token>`. The scheme is read in any case, and whitespace around the token
  is ignored. A cookie never opens the API, and the admin pages refuse a request that carries `Authorization`.
- `/healthz` needs no token.

## Requests

| Request | Success | Errors |
|---|---|---|
| `GET /industries` | `200`, the active industry picklist | |
| `POST /matches` | `201` and `Location`, the stored match | `400` `invalid_request`; `422` `invalid_fact` with `field`; `409` `analysis_not_ready` with `Retry-After`; `422` `analysis_package_not_found`; `502` `analysis_unavailable`; `502` `analysis_contract_mismatch`; `503` `analysis_not_configured` |
| `GET /matches/<match_id>` | `200`, the stored match with `current` and `superseded_by` as they stand now | `404` `match_not_found` |
| Any other path or method under `/api/v1` | | `404` `route_not_found`; `405` `method_not_allowed` with `Allow` |
| Every request | | `401` `unauthorized` with `WWW-Authenticate: Bearer`; `403` `scope_required`; `500` `internal_error` |

- The token is checked before anything else, so a request without one answers 401 on any path.
- The request body is read strictly. A body that is not JSON, lacks `application`, names a field this contract does
  not define, or holds a value outside a closed set (`product`, `entity`) answers 400 `invalid_request`.
- A field that parses but no fact can hold answers 422 `invalid_fact`, and `error.field` is its JSON pointer:
  `business_state` that is not a postal code, `business_start_month` that is not `YYYY-MM` or is after the current
  month, `estimated_fico` outside 300 to 850 or with `min` above `max`, `requested_amount_cents` of 0 or less, and
  `industry_suggestion` that is not an active industry id.
- Every response body is JSON and carries `Cache-Control: no-store`. An error body is this envelope, with the code's
  one fixed message from the catalog below:

```json
{"error": {"code": "invalid_fact", "message": "a field holds a value this API does not accept", "field": "/application/business_state"}}
```

## How a match is made

1. The server fetches the analysis package itself with `GET <ANALYSIS_API_URL>/packages/<id>`, so a caller cannot
   alter a figure. A processing package answers 409 with the analysis API's `Retry-After`. A package the analysis
   service does not know answers 422. A body outside the analysis v1 contract answers 502.
2. It assembles the facts at today's date in UTC. The rules are in the next section.
3. In one transaction it reads every lender's current revision, evaluates each active lender that offers the
   product, and stores the match with the revision each verdict read. A lender that is a draft, paused or does not
   offer the product is listed in `inactive`.

A stored match never changes. `GET /matches/<id>` adds two facts that can: `current` on each verdict says whether
the lender's current revision is still the one the verdict read, and `superseded_by` names the newer match a person
made from this one on the match page.

## Facts

Each fact appears once, known or not. A number is an inclusive interval `{"min", "max"}`; `max` null is unbounded.

- `basis` says where a known value comes from: `printed` by the analysis, `stated` on the application, or
  `confirmed` by a signed-in person on the match page.
- `gap` says why a fact is unknown: `not_supplied` (no package, or no value), `no_figures`, `not_established` (the
  analysis published null), `currency_refused`, `not_usd`, `analysis_review_required`, or `needs_confirmation`.
- `seen` is a value the inputs show but do not prove, such as the suggested industry or a figure of a package that
  needs review. It is never evaluated.

The analysis facts follow the analysis contract:

- When `review.required` is true, every analysis fact is unknown with `analysis_review_required`, and its value is
  `seen`.
- Money needs `figures.currency` of `USD`.
- `worst_month_negative_days` and `worst_month_deposits` come from the included accounts' statement periods. A period
  of 28 to 31 days, or of at most 31 days mostly in one calendar month, stands for the month holding most of its
  days. A longer period adds `[0, n]` to each month it touches, and the worst month then holds at least `ceil(n / m)`
  of its `n` negative days over `m` months. A period without both dates may fall in any month: it adds to every month
  and is also a month of its own. Several periods in one month give negative days from their maximum to their sum,
  and deposits that add. A period's deposits lie between its `true_revenue_count` and its `deposit_count`.
- `new_position` is the latest listed month's `active_positions` plus one, up to plus `possible_positions` more.
- `statement_months` runs from the calendar months the dated periods stand for or cover in full, up to
  `figures.months`.
- `funder_payment_history` is true when `figures.funders` lists a confirmed funder, and unknown otherwise.

The industry, default history, home-based status and open lawsuits need a person's confirmation. Every other
application value counts as `stated`.

## Verdicts

A rule applies to a deal when every condition in its `when` holds, and then checks its requirement. Each check is
three-valued: `pass` when every value the facts allow passes, `fail` when every value fails, and `unproven`
otherwise, with `why`: `fact_unknown`, `straddles` (the interval crosses the bound) or `scope_unknown` (the rule may
apply, and the fact that decides whether it does is unknown). A rule whose condition is false is `not_applicable`.

- `no_match` when a check fails.
- `review` when no check fails but one is unproven, or a `condition` note may apply. A condition note is text no rule
  captures yet; an `info` note never changes a verdict.
- `match` otherwise.

On the match page a reviewer or editor can confirm facts and waive a check or a condition note with a reason.
Submitting makes a new match that supersedes the old one, with the analysis fetched again and every lender's
current revision. A waiver holds only while the lender revision and the analysis revision it was given on stay the
same; otherwise it is listed in `stale_waivers` and not applied.

## Versioning

The path carries the major version and `api_version` the minor one. Within 1.x a change only adds: a new response
field, or a new value of an open string (`fact`, `gap`, `why`, `source`). A response field that can be null is always
present. Removing, renaming or retyping a field, a new value of a closed set (`status`, `outcome`, `kind`, `scope`,
`basis`, `product`, `entity`, an error code), or a different reading needs v2.
